# `roco-daily-bot` 工程合作约束准则

## 一、项目状态以 Git 为最高事实来源

这是整个合作中最重要的原则。

> **GitHub 仓库中的实际代码与文档，是项目当前状态的唯一权威来源；聊天记录不是。**

如果出现：

```
聊天记录
    VS
GitHub 当前代码
```

永远以：

```
GitHub 当前代码
```

为准。

因此，当我需要修改已有代码时，不能仅凭过去的聊天记忆推断代码结构，而应该：

```
读取当前仓库
    ↓
确认当前代码
    ↓
理解现有设计
    ↓
提出修改
    ↓
实施修改
```

这条规则尤其用于防止长期项目中由于上下文丢失产生的“AI 幻觉”。

---

# 二、`PROJECT.md` 是项目状态的权威文档

`PROJECT.md` 负责回答：

> **“这个项目现在是什么状态？”**

它应该记录：

- 项目目标
- 核心原则
- 技术方向
- 功能阶段
- 当前阶段
- 已确定的设计
- 尚未确定的事项
- 开发记录

但有一个重要原则：

> **没有真正讨论、验证或决定的事情，不要提前写进 `PROJECT.md`。**

例如：

```
OCR 使用 PaddleOCR
```

如果我们还没决定，就不能提前写进去。

应该保持：

```
OCR 引擎尚未确定
```

这样 `PROJECT.md` 才真正代表项目状态，而不是“计划书”。

---

# 三、`DECISIONS.md` 记录“为什么”

`PROJECT.md`：

> **现在是什么？**

`DECISIONS.md`：

> **为什么是这样？**

任何可能影响架构、技术路线或未来重构的重要决定，都应该记录下来。

例如：

```
为什么使用固定 ROI？
为什么不用 YOLO？
为什么选择 SQLite？
为什么不读取游戏内存？
为什么保存原始 OCR 结果？
```

推荐使用 ADR（Architecture Decision Record）形式：

```
ADR
├── 决定
├── 背景
├── 原因
├── 影响
├── 日期
└── 状态
```

特别重要的一点：

> **已经经过验证并确定的设计，不应该仅仅因为“看起来可以优化”就随意推翻。**

修改既有决策时，应当创建新的 ADR，而不是直接覆盖旧决策。

这样能够保留：

```
原来的决定
    ↓
为什么做
    ↓
后来发现什么问题
    ↓
为什么改变
```

---

# 四、`CHANGELOG.md` 记录“发生了什么”

它与 `DECISIONS.md` 不同。

```
PROJECT.md
→ 当前状态

DECISIONS.md
→ 为什么这么设计

CHANGELOG.md
→ 项目发生过什么变化
```

例如：

```
v0.1
实现屏幕截图

v0.2
实现 ROI

v0.3
加入 OCR

v0.4
加入状态机
```

它主要用于建立项目历史。

---

# 五、聊天负责“讨论”，仓库负责“沉淀”

我们的职责可以明确分成：

```
聊天
↓
讨论
↓
分析
↓
尝试
↓
决定
↓
验证
↓
写入仓库
```

聊天中的想法不自动等于项目设计。

例如我说：

> “我们可以考虑使用 YOLO。”

这只是**讨论中的候选方案**。

不能因此就在 `PROJECT.md` 写：

```
使用 YOLO
```

只有经过讨论并决定后，才进入正式项目文档。

---

# 六、所有重要结论都应该经过“验证 → 固化”

我们采用：

```
假设
 ↓
实现
 ↓
实际测试
 ↓
确认结果
 ↓
记录
```

例如：

> “游戏技能区域应该是固定位置。”

这只是一个假设。

经过多个分辨率测试后，如果确认：

> 1080p 和 1440p 下 ROI 可以通过比例换算得到。

这时才能成为正式设计，并记录到：

```
PROJECT.md
```

以及必要时：

```
DECISIONS.md
```

---

# 七、不确定的信息必须保持“不确定”

工程中明确区分：

### 已确认

有实际证据。

### 暂定

目前认为合理，但还没有充分验证。

### 未确定

尚未决定。

### 否决

讨论过，但明确不采用。

例如：

```
OCR 引擎：
暂未确定

ROI：
初步考虑固定 ROI

数据库：
暂未确定
```

而不是为了让文档看起来完整，提前填入答案。

---

# 八、不要过度设计 MVP

这是这类项目非常重要的一条。

我们应该遵循：

> **只实现当前阶段真正需要的东西。**

例如 Phase 0：

```
项目初始化
```

就不应该提前创建：

```
src/
tests/
data/
database/
OCR/
state_machine/
GUI/
```

除非当前阶段真的需要。

你原本提出的：

> **真正需要的时候再创建**

我会保留为明确规则。

---

# 九、MVP 优先验证“最关键的不确定性”

项目不是按照：

```
先把所有架构设计完
↓
再开始写代码
```

而是：

```
找出最大的技术风险
↓
做最小实验
↓
验证
↓
再决定架构
```

例如我们怀疑：

> 游戏技能名称是否能稳定 OCR？

那么 MVP 就应该优先验证：

```
截图
→ ROI
→ OCR
→ 技能名称
```

而不是先开发完整数据库、GUI 和状态机。

---

# 十、原始数据优先于加工数据

这个原则你原来的设计非常重要，我建议正式保留。

程序应该尽可能保存：

```
原始截图
原始 OCR 结果
识别时间
识别区域
程序判断结果
```

而不是只保存：

```
最终结论
```

例如：

```
截图
 ↓
OCR：
“火焰冲击”
 ↓
程序：
识别为技能 A
```

最好保留原始信息。

这样未来发现 OCR 判断错误时，可以：

```
重新读取历史数据
↓
修改识别算法
↓
重新分析
```

而不用重新打游戏。

---

# 十一、功能开发遵循“小步提交”

推荐：

```
一个明确功能
    ↓
实现
    ↓
测试
    ↓
Git commit
```

而不是一次积累几十个未验证修改。

例如：

```
feat: add window detection

feat: add screenshot capture

feat: add ROI extraction

feat: add OCR prototype
```

这样如果某一步出了问题，可以非常容易回退。

---

# 十二、阶段完成时必须进行 Project Sync

这是我们长期合作的“检查点机制”。

每完成一个重要阶段，我们生成一次：

```
Project Sync
```

内容至少包括：

```
当前版本
已完成
当前代码结构
已知问题
已验证内容
已确定决策
未确定事项
下一阶段
```

然后同步到 Git。

这样即使：

```
换聊天
换模型
隔几个月回来
```

都可以通过：

```
PROJECT.md
DECISIONS.md
CHANGELOG.md
Git history
```

恢复项目上下文。

---

# 十三、AI 修改代码前必须尊重现有架构

以后如果我看到：

```
some_weird_code()
```

不能直接说：

> “这个写得不好，我们重构。”

必须先检查：

```
PROJECT.md
DECISIONS.md
当前代码
```

因为这个代码可能是：

> **为了适配游戏特殊行为而刻意保留的。**

如果确实需要修改：

```
当前设计
 ↓
发现问题
 ↓
提出修改
 ↓
讨论
 ↓
决定
 ↓
更新 DECISIONS.md
 ↓
修改代码
```

---

# 十四、不得为了“完成任务”而虚构实现结果

这条虽然不是你原始协议的核心，但我建议加入。

我不能把：

```
理论上可行
```

说成：

```
已经验证可行
```

也不能把：

```
代码应该能运行
```

说成：

```
已经测试通过
```

特别是涉及游戏 UI、Windows API、OCR、第三方库时。

如果没有实际验证，就明确写：

```
尚未验证
```

---

# 十五、项目安全边界必须保持明确

目前已经确定：

### 不读取游戏内部数据

不进行：

- 进程内存读取
- DLL 注入
- 游戏文件修改
- 网络封包分析

### 不自动控制游戏

不实现：

- 自动点击
- 自动释放技能
- 自动移动
- 自动选择目标
- 自动战斗

因此即使后续技术上发现某种“更简单”的方法，也不能因为方便就擅自突破这个边界。

如果未来要改变，需要**明确讨论并更新项目决策**。

---

# 十六、项目命名也保持一致

我们现在项目已经从原来的 PvP Logger 转向了：

> **洛克王国清日常工具**

因此项目名称：

```
roco-daily-bot
```

这是当前项目名。

但这里还有一个需要注意的地方：

**“bot”这个名字与之前“不自动控制游戏”的原则存在潜在冲突。**

所以我不会擅自把它解释成“自动操作游戏的 Bot”。

目前应该理解为：

> **roco-daily-bot 是仓库/项目名称；具体功能边界以 `PROJECT.md` 为准。**

等我们正式重新编写 `PROJECT.md` 时，再决定是否需要把“清日常”定义为自动化操作。

---

# 最终合作模型

我建议以后我们整个项目都遵循这个循环：

```
                 ┌──────────────┐
                 │   GitHub     │
                 │ 真实项目状态  │
                 └──────┬───────┘
                        │
                        ↓
                  阅读当前代码
                        │
                        ↓
                 ┌──────────────┐
                 │    讨论      │
                 │  分析/设计   │
                 └──────┬───────┘
                        │
                        ↓
                  最小实现 / MVP
                        │
                        ↓
                     实际测试
                        │
                        ↓
                    得到证据
                        │
                        ↓
                ┌───────────────┐
                │  固化项目状态  │
                ├───────────────┤
                │ PROJECT.md    │
                │ DECISIONS.md  │
                │ CHANGELOG.md  │
                └───────┬───────┘
                        │
                        ↓
                    Git Commit
                        │
                        └────────→ 下一轮
```

### 最核心的五句话

如果以后只记住五条，我建议就是：

> **1. GitHub 当前代码是真实状态，聊天记录不是。**

> **2. `PROJECT.md` 记录“现在是什么”。**

> **3. `DECISIONS.md` 记录“为什么这么做”。**

> **4. `CHANGELOG.md` 记录“发生了什么”。**

> **5. 不确定的事情先验证，不要为了推进项目而假设它已经成立。**

接下来我们就可以**从 Phase 0 重新开始**。第一件事不是写代码，而是按照这个协议，把已经改变目标的项目重新建立一个干净的 `PROJECT.md`。
